1. Data Requirements

1.1 Structured Data (SQL Tables)

  • 8–12 tables in a star/snowflake schema with clear FK relationships
  • 5M+ total rows — enough that agents can’t brute-force scan
  • Must have multi-hop join paths (3–4 hops from fact to outermost dimension)
Table TypeExamplesPurpose
Dimension (3–4)Location, Product, Supplier, EmployeeForce joins to get attributes (country, category, quality tier)
Core factTransaction / Order headerHub connecting customers, locations, products
Detail factTransaction line itemsLine-level detail that must join to parent fact
Secondary facts (3–4)Returns, Reviews, Loyalty, InventoryRequire multi-hop joins to reach dimensions
Bridge/associationPromotions, CampaignsLinks two dimensions — creates cartesian risk

1.2 Unstructured Data (Documents)

  • 3+ document collections with different content types
  • 1,000+ documents (enough to require search, not just scan)
  • Must contain specific verifiable numbers that benchmark questions reference
CollectionContentPurpose
Entity descriptionsProduct specs, patient profiles, asset detailsTests entity-level document retrieval
Audit/compliance reportsQuality scores, findings, recommendationsTests correlation: structured metrics vs document findings
Industry researchMarket data, KPIs, trends with specific numbersTests grounding in documents vs hallucinating benchmarks

1.3 Data Skew (Critical)

Uniform data makes ALL benchmark questions useless. When distributions are flat, the “wrong approach” gives the same answer as the correct one. There is nothing to differentiate.

2. Structural Data Gaps

This is the #1 proven differentiator. Structural gap detection is the strongest proven differentiator in live benchmarks. Real-world data always has holes — your benchmark data must too.

Why gaps matter: When a table has zero rows for a specific segment, an agent that blindly aggregates includes zeros (wrong averages, wrong rankings). An agent that detects the gap flags it or excludes correctly. Databricks Genie consistently hallucinates data for missing segments instead of detecting the absence.

Gap TypeReal-World ReasonHow to CreateBenchmark Impact
Program not in all marketsFeature/program launched market by marketDelete a transaction type for 2 regionsAgent includes zeros → deflated averages
No feedback for some productsReview system doesn’t cover all categoriesDelete reviews/feedback for one categoryAgent hallucinates rating vs detects gap
No digital tracking in some marketsNewer markets use manual systemsDelete tracking records for 1 regionAgent hallucinates metrics vs flags impossibility
Promo/campaign types vary by marketNot all campaign types available everywhereDelete one campaign type for 2 regionsAgent reports wrong coverage
Reason codes not tracked everywhereSome markets don’t capture reason codesNULL out reason column for 1 regionAgent hallucinates reasons vs detects NULLs
Verification rule: For each gap, compute the answer with and without the missing data. The difference must be >20%. If the gap doesn’t meaningfully change the answer, it won’t differentiate agents.

Gaps must be realistic. An auditor or customer should look at the data and say “yes, this is how our data looks.”

3. Competitor Failure Patterns (Ranked)

TIER 0 Structural Gap Detection — Strongest

  • Table has zero rows for a specific segment (country, category)
  • Snowflake detects with LEFT JOINs guided by semantic view
  • Competitor uses INNER JOINs → silently drops missing segments or hallucinates values
  • Proven across multiple domains: strongest pattern tested; consistently largest scoring gaps

TIER 1 Document Grounding + SQL — Strong

  • Questions requiring BOTH a SQL computation AND a document search
  • Snowflake: single agent context with Cortex Analyst + Cortex Search
  • Competitor: separate SQL agent + Knowledge Agent → loses coherence when combining
  • Trigger phrase: “Search our [topic] research for industry benchmarks to compare”

TIER 1 Cartesian Product Trap — Strong

  • Ratio of two independently aggregated metrics from different fact tables
  • Naive join creates M×N explosion — values off by 3x or more
  • Example: “Promotion spend per returned item by category”

TIER 2 Wrong Denominator — Moderate

  • Agent uses total count instead of filtered subset (e.g., all records vs only qualifying members)
  • Only works if penetration varies significantly by segment

TIER 2 CTE Planning Failure — Moderate

  • Executive summary requiring 4+ independent calculations
  • Works better when each sub-query touches different tables

TIER 3 Negation / Metric Hallucination — Weak

  • Unreliable — competitor often handles negation correctly by splitting queries
  • Metric hallucination affects both platforms equally

4. Question Phrasing Guide

WIN Phrasing patterns that create gaps

Pattern A: “Are there any [entities] where [metric] CANNOT be calculated — and why?”

Forces LEFT JOIN reasoning to detect zero-row segments. Competitor uses INNER JOINs and silently drops or hallucinates. Strongest observed pattern.

Pattern B: “Search our [research topic] for industry benchmarks to compare”

Forces combined SQL + document search. Snowflake handles natively; competitor routes to two separate sub-agents. Consistently strong pattern.

Pattern C: Business question requiring pre-aggregation

Questions where naive joins create cartesian products. Frame as business question, not computation recipe. Consistently strong pattern.

Pattern D: Double negation across tables

“Members who NEVER did X AND NEVER did Y” where X and Y are in different tables. Moderate to strong pattern.

TIE Phrasing that produces no gap (avoid)

  • Explicit computation recipes — “Calculate SUM(A)/COUNT(B) grouped by C” → both follow instructions
  • Simple single-join aggregations — “Completion rate by region” → both handle fine
  • Uniform data questions — if rates are identical in every region, no trap fires

LOSE Phrasing that hurts Snowflake (avoid)

  • Ambiguous metrics — “average revenue per member” could mean per-row avg vs SUM/COUNT(DISTINCT). Fix: be hyper-explicit.
  • Missing semantic view config — if a join or metric isn’t defined, Cortex Analyst blocks the query (scores 1) while competitor infers joins from column names.
  • Stale ground truth — if you modified data but didn’t recompute answers, Snowflake gets penalized for being correct.

5. Scoring Framework

DimensionScore 1–5What It Measures
Accuracy1–5Are the numbers correct? Within 5% of ground truth?
Groundedness1–5Did the agent use actual data (SQL, doc search) or hallucinate?
Relevance1–5Did the agent answer the actual question asked?

Total: /15 per question. Use Snowflake Cortex COMPLETE (Claude Sonnet) for automated scoring. Provide question, expected answer with key numbers, agent output, and scoring rubric.

Ground truth rules:

  • Always compute from actual loaded data via SQL — never assume from data generators
  • Include both “correct approach” and “wrong approach” values in expected answer
  • Recompute ALL answers after ANY data modification — cascading effects are real

6. Platform Setup Checklist

Snowflake Cortex Agent

  1. Load structured data into tables
  2. Upload documents to internal stage → populate DOC table (use direct read for .txt, skip PARSE_DOCUMENT)
  3. Create Cortex Search service on document table
  4. Create Semantic View via Autopilot, then manually verify:
    • All join relationships exist (especially multi-hop paths: 3–4 tables deep)
    • SUM metrics for key measures (revenue, refunds, quantity)
    • Descriptive comments on key columns (status values, date meanings, filter conditions)
  5. Create Cortex Agent with both Analyst (semantic view) and Search tools
  6. Add general instructions with data rules
  7. Do NOT add VQRs — tests raw agent capability

Databricks Genie

  1. Load structured data into Unity Catalog tables
  2. Load documents into a doc table
  3. Create Genie Space with all tables + general instructions (same data rules)
  4. Create Knowledge Assistant agent for document search
  5. Create Supervisor agent routing between Genie + Knowledge Assistant
  6. Do NOT add sample queries — tests raw agent capability
  7. Apply identical structural gap DELETEs as Snowflake for fair comparison

9. Extending to New Domains

This playbook works for any domain. The key ingredients are:

  1. Star schema with 3–4 hop join paths (fact → detail → dimension → parent dimension)
  2. Unstructured corpus with verifiable numbers (not generic text)
  3. Controlled data skew on the dimensions that questions target
  4. Structural data gaps that are realistic for the domain
  5. Business-framed questions that don’t give away the computation method
  6. Ground truth computed from actual loaded data
